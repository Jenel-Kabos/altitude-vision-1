# Membership Backfill — First Pilot Runbook (Phase 1H.2)

**Status: certification document. This runbook does NOT execute a backfill.
It describes, sequentially, the checks and commands that must be performed
before, during and after the first live single-membership pilot. The pilot
itself is deferred to Phase 1H.3 and requires explicit human authorization
via that phase.**

Related phases (must all be certified GREEN before this runbook is used):

- USER-TENANT-MEMBERSHIP-ARCHITECTURE-1G — audit
- USER-TENANT-MEMBERSHIP-ARCHITECTURE-1H — dry-run engine
- USER-TENANT-MEMBERSHIP-ARCHITECTURE-1H.1 — controlled apply mechanism

Related artefacts:

- `server/scripts/backfillTenantMembershipsDryRun.js` (read-only engine)
- `server/scripts/backfillTenantMembershipsApply.js` (CAS-guarded apply)
- `server/__tests__/backfillTenantMembershipsDryRun.mongo.integration.test.js`
- `server/__tests__/backfillTenantMembershipsApply.mongo.integration.test.js`

Hard constants used by this document (do not paraphrase — the static
runbook test asserts these strings verbatim):

- `PILOT_TENANT_ID=TO_BE_SELECTED_DURING_AUTHORIZED_PREFLIGHT`
- `FIRST_PILOT_MAX_WRITES = 1`
- `--limit 1`

## A. Scope

This runbook governs the very first live application of a **single**
membership backfill on a **single** tenant. It converts one `OrgMembership`
row for that tenant from `businessRole: null` to a canonical
`TENANT_BUSINESS_ROLES` value, using the 1H.1 apply script — nothing else.

- Only **one** membership is touched. Cap: `FIRST_PILOT_MAX_WRITES = 1`.
- Only the **selected** tenant is touched. Every other tenant is
  guaranteed untouched by the `--tenant <T0>` filter + apply-time CAS.
- Any subsequent batch (limit > 1) requires a separate authorization phase
  and its own runbook; this document does **not** cover it.
- **1H.2 explicitly forbids production write during the phase itself.** The
  live pilot is Phase 1H.3.
- **Automatic 1I progression is explicitly forbidden.** Removal of the
  legacy fallback (`resolveTenantMembership.allowLegacyRoleFallback`) is
  gated on Phase 1I, which cannot start automatically after 1H.3.

## B. Preconditions

1. All of 1A → 1H.1 certified GREEN.
2. `git rev-parse HEAD` recorded and captured in the pilot evidence file
   (Section N). The apply script hash and the dry-run script hash must be
   identical between pre-flight and apply — code version pinning is
   mandatory.
3. `docs/1H.2-pilot-runbook.md` (this file) unmodified between pre-flight
   and apply.
4. The pilot operator has read this runbook end-to-end and has explicit
   authorization from the tenant owner and from Altitude Vision engineering
   leadership to run 1H.3.
5. No other backfill, migration or schema change is in flight.

## C. Tenant selection

`PILOT_TENANT_ID=TO_BE_SELECTED_DURING_AUTHORIZED_PREFLIGHT`

The pilot tenant `<T0>` is chosen during the authorized pre-flight window
(Section D). Selection criteria — every one MUST hold before the tenant
qualifies:

- `PlatformTenant.status === 'active'`.
- `rootOrgUnit` exists and is reachable.
- The tenant has at least one existing active `OrgMembership` on
  `rootOrgUnit`.
- A read-only dry-run for `--tenant <T0>` returns candidate rows exclusively
  in the following classifications: `UPDATE_CANDIDATE` (with confidence
  `HIGH`), `ALREADY_CANONICAL`, or any `SKIP_*` category. It must NOT
  return `MULTI_TENANT_MANUAL_REVIEW`, `MANUAL_REVIEW`, `CONFLICT` or
  `EXTERNAL_ROLE` rows implicating the tenant.
- Ideally the founder is known — a matching `TenantApplication` with
  `provisionedTenant === T0` and `provisionedMembership` populated.
- The tenant has a low overall volume: fewer than 20 active tenant-root
  memberships. Large tenants are reserved for later batches.
- No suspended or revoked membership on the tenant qualifies for backfill
  under any circumstance.

Do NOT hardcode a tenant ObjectId in this file, in the apply script, or in
any test. The tenant is passed on the command line at pre-flight and apply
time.

## D. Read-only pre-flight

Connection contract (fail closed):

- `MONGO_URI_READONLY` is **REQUIRED FOR PREFLIGHT** and must explicitly
  target the `altitudevision` database.
- `MONGO_URI` is **FORBIDDEN FOR PREFLIGHT**. The scanner never falls back to
  it, even when it is present.
- `MONGODB_FINANCIAL_INTEGRATION_URI` is test-only and is never a pre-flight
  fallback.
- Absence or an empty value of `MONGO_URI_READONLY` is a **NO-GO** and fails
  before any Mongo connection with `READONLY_URI_REQUIRED`.
- A missing or different database name fails before connection with
  `READONLY_DATABASE_REQUIRED`.
- The CLI logs only scheme, database name and a SHA-256 host fingerprint. It
  never logs the URI, username, password or full hostname.
- The variable name is a code-enforced connection contract. The actual Atlas
  database role remains an externally verified infrastructure prerequisite;
  URI syntax cannot prove that the credential is read-only.

Recommended connection preference, in order:

1. Production read replica with read-only credentials.
2. A recent production snapshot restored into a staging replica set.
3. A production read-only connection **only** if the infrastructure exposes
   dedicated read-only credentials AND explicit authorization has been
   granted.

Run the pre-flight dry-run against the selected tenant:

```
MONGO_URI_READONLY='<provided securely outside shell history>' \
  node server/scripts/backfillTenantMembershipsDryRun.js
```

The script currently emits a whole-database report; extract the tenant
subset with a tenant filter at read time, or (preferred) rely on the apply
script's `--tenant <T0>` filter which is proven to isolate writes.

Persist the pre-flight JSON to a local file:

```
artifacts/backfill/1H2/tenant-<T0>-preflight.json
```

`artifacts/` should be `.gitignore`d so pre-flight JSON never lands in the
repo. If it isn't yet gitignored, add it before pre-flight is executed.

Capture from the pre-flight JSON, into the evidence file (Section N):

- `metadata.generatedAt`
- `metadata.version` (must equal `USER-TENANT-MEMBERSHIP-ARCHITECTURE-1H`)
- The full row for the candidate membership (membershipId, userId,
  tenantId, currentBusinessRole, proposedBusinessRole, source, confidence,
  classification, action).
- The computed **dry-run manifest hash** — see Section F.

## E. Candidate review

The candidate row proposed by the pre-flight MUST satisfy every one of the
following (each condition is asserted verbatim by
`server/__tests__/backfillPilotRunbook.static.test.js`):

- `action === 'UPDATE'`
- `classification === 'UPDATE_CANDIDATE'`
- `confidence === 'HIGH'`
- `currentBusinessRole === null`
- `proposedBusinessRole` ∈ `TENANT_BUSINESS_ROLES`
- `membership.status === 'active'`
- Tenant root confirmed (dry-run has already resolved `orgUnit` to
  `PlatformTenant.rootOrgUnit`)
- `User` valid: exists, `isActive !== false`, `isTechnical !== true`
- No `CONFLICT` diagnostic
- No `MANUAL_REVIEW` diagnostic
- No `MULTI_TENANT_MANUAL_REVIEW` diagnostic
- No `EXTERNAL_ROLE` diagnostic
- Tenant isolation confirmed: the candidate's `tenantId` equals `<T0>`.

Any deviation is a STOP.

## F. Explicit human sign-off

Before proceeding, the pilot operator MUST print and complete the
following checklist. Each item is required — no partial approvals.

- [ ] tenantId correct
- [ ] membershipId correct
- [ ] userId correct
- [ ] tenant name correct
- [ ] currentBusinessRole == null
- [ ] proposedBusinessRole correct
- [ ] source understood
- [ ] confidence == HIGH
- [ ] User.role reviewed
- [ ] multi-tenant risk checked
- [ ] membership status == active
- [ ] no conflict
- [ ] no external role
- [ ] manifest hash captured
- [ ] rollback data captured
- [ ] --limit == 1
- [ ] operator explicitly approves execution

**dryRunManifestHash** (SHA-256 over the sorted, timestamp-free candidate
manifest — see 1H.1 `computeDryRunHash`) MUST be captured verbatim and
attached to the operator's approval.

If the pre-flight is re-run for any reason, the previous approval becomes
invalid. The checklist and the hash MUST be re-captured.

## G. Backup / rollback readiness

Two levels of rollback exist:

- **LEVEL 1 — logical rollback.** Targeted CAS-inverse update guided by the
  ActionLog row(s) produced during the pilot. See Section M.
- **LEVEL 2 — database recovery.** Requires an external backup/snapshot of
  the production Mongo cluster. `DATABASE BACKUP AVAILABILITY: UNKNOWN —
  MUST BE CONFIRMED BEFORE LIVE PILOT`. If backup availability cannot be
  confirmed and its recency documented before pilot minute-1, the pilot is
  NO-GO. This runbook does not claim a backup exists — its existence is a
  precondition that must be verified externally.

## H. Pilot execution command (documented, NOT executed in 1H.2)

Once the pre-flight and sign-off are complete, and only under Phase 1H.3
authorization, the pilot command is:

```
node server/scripts/backfillTenantMembershipsApply.js \
  --live \
  --commit \
  --tenant <T0> \
  --limit 1
```

Do NOT execute this command inside Phase 1H.2. Its role here is
documentary. Every flag is mandatory:

- `--live` — accept a non-test connection target.
- `--commit` — perform writes. `--commit` without `--live` is refused at
  the argument-parser level (APPLY-17).
- `--tenant <T0>` — validated existence-check before candidates are
  considered. `--tenant <invalid>` fails closed (`TENANT_NOT_FOUND`).
- `--limit 1` — hard cap on writes for the first pilot. The apply script
  additionally reports `SKIPPED_BY_LIMIT` for any row past the cap.

Environment: `MONGO_URI` must point at the target production write cluster
using restricted-write credentials if the infrastructure supports the
distinction (Section U).

This live-apply credential is separate from pre-flight. `MONGO_URI_READONLY`
cannot perform the pilot write and must not replace the explicitly authorized
restricted-write `MONGO_URI` used by the apply command.

## I. Immediate post-write verification

Immediately after the pilot returns, capture the JSON report emitted on
stdout and assert:

1. `metadata.mode === 'apply'`
2. `metadata.tenantFilter === '<T0>'`
3. `metadata.limit === 1`
4. `metadata.dryRunHash === <the hash captured in Section F>`
5. `summary.APPLIED ∈ {0, 1}`
6. `summary.ATTEMPTED ≤ 1`
7. `summary.ACTION_LOGS_CREATED === summary.APPLIED`
8. `summary.CAS_SKIPPED === summary.ATTEMPTED - summary.APPLIED`
9. `summary.SKIPPED_BY_LIMIT === max(0, ELIGIBLE_AFTER_FILTER - 1)`

Then read the target membership directly and assert:

- `businessRole === proposedBusinessRole` (from the sign-off row)
- `status === 'active'` (unchanged)
- `user`, `orgUnit`, `roleInUnit` unchanged
- `OrgMembership.countDocuments({})` unchanged from pre-flight snapshot

Then read the target User:

- `User.role` unchanged
- `User.isActive` unchanged
- `User.status` unchanged (if the field was set pre-flight)
- `historiqueRoles` unchanged (no legacy role-change record injected)

## J. Second dry-run

Re-run `backfillTenantMembershipsDryRun.js` against the same tenant. The
target membership MUST now be classified `ALREADY_CANONICAL`. Assert:

- The target row's `classification === 'ALREADY_CANONICAL'` and
  `action === 'SKIP'`.
- No new `CONFLICT` row exists for the tenant.
- No new `MANUAL_REVIEW` row exists that references the pilot User.
- No unrelated tenant's classifications changed relative to the pre-flight
  hash (a full-DB re-hash minus the target row must match).

## K. ActionLog verification

Query ActionLog for the batch:

```
ActionLog.find({
  action: 'tenant_membership_backfill_1h1',
  'metadata.regularization.batchId': <captured batchId>,
})
```

- Count MUST equal `summary.APPLIED`.
- Each row's `metadata.regularization.manifestHash` MUST equal the
  captured dry-run hash.
- Each row's `metadata.regularization.operation === 'apply'`.
- Each row's `metadata.regularization.before === { businessRole: null }`.
- Each row's `metadata.regularization.after.businessRole` matches the
  proposed role.

## L. GO / STOP criteria

**GO** only if every one of the following holds:

- Sign-off checklist complete.
- Backup availability confirmed (Section G LEVEL 2).
- Restricted-write credentials confirmed (Section U) or the gap
  documented and accepted by the tenant owner.
- Pre-flight candidate satisfies every Section E rule.
- `dryRunManifestHash` recorded.
- `git rev-parse HEAD` at pre-flight equals `git rev-parse HEAD` at apply.
- No other backfill, migration or schema change in flight.

**STOP** if any of:

- manifest hash changes after approval;
- candidate count changes unexpectedly;
- candidate classification changes;
- confidence != HIGH;
- candidate becomes multi-tenant ambiguous;
- currentBusinessRole no longer null;
- membership status changes;
- tenant not active;
- CAS fails unexpectedly;
- ActionLog mismatch after apply;
- more than 1 attempted write;
- any unrelated row changes;
- User changes;
- tenant isolation violated.

No automatic continuation. Every STOP requires a fresh pre-flight and a
fresh sign-off.

## M. Rollback procedure

Rollback is scoped, CAS-protected and ActionLog-driven. Never
`updateMany`. Never `bulkWrite`. Never blind `save`.

Source of authority: the ActionLog row produced during the pilot. Fields
consumed: `metadata.regularization.batchId`, `metadata.regularization.resourceId`
(the `membershipId`), `metadata.regularization.before.businessRole`
(the previous value — for the first pilot always `null`),
`metadata.regularization.after.businessRole` (the value the pilot wrote),
and `metadata.regularization.manifestHash`.

Conceptual CAS-inverse update:

```
OrgMembership.updateOne(
  { _id: <membershipId>, businessRole: <newBusinessRole>, status: 'active' },
  { $set: { businessRole: <previousBusinessRole /* null for first pilot */> } }
)
```

Rollback safety — the CAS filter includes `businessRole: <newBusinessRole>`
so that a subsequent canonical change (e.g. an Admin changing the role via
`/api/members` after the pilot) makes the CAS filter no longer match. The
rollback MUST NOT overwrite that canonical change. If `matchedCount === 0`
the result is `ROLLBACK_CONFLICT` and rollback stops with `MANUAL_REVIEW`.

Emit a companion ActionLog with the same schema and
`metadata.regularization.operation === 'rollback'`. The unique index on
`(batchId, resourceType, resourceId, operation)` prevents duplicate rollback
entries.

**1H.2 does NOT implement or execute the rollback.** This section defines
the contract only. Rollback tooling is deferred to Phase 1H.3 or a
successor phase and is out of scope for 1H.2.

## O. Conditions before 1I

Phase 1I (Legacy Fallback Retirement) MUST NOT start until:

1. The first pilot (1H.3) has landed and passed every Section I/J/K
   verification.
2. A second, larger controlled batch (limit > 1) has landed with the same
   verification quality, under a separate phase.
3. A full-DB dry-run reports zero remaining `businessRole: null` on
   active tenant-root memberships (candidates classified
   `UPDATE_CANDIDATE`).
4. `resolveTenantMembership`'s legacy fallback (`allowLegacyRoleFallback`)
   has been proven unreachable in live traffic for at least one full
   observation window agreed with the tenant owner.

**Automatic 1I progression is explicitly forbidden.** This runbook does
not authorize 1I under any circumstances.

## P. DB user permissions (Section U reference)

- **Pre-flight connection:** read-only credentials.
- **Pre-flight environment:** `MONGO_URI_READONLY` only; `MONGO_URI` is
  forbidden and no implicit fallback exists.
- **Apply connection:** restricted-write credentials if the infrastructure
  supports the distinction. Never a superadmin account when
  restricted-write suffices.

If the platform does not currently support this separation, document the
gap and treat it as a NO-GO conditional on the tenant owner accepting the
risk in writing.

## Q. Production write window

- Named operator identified.
- No other backfill, migration or schema change in flight.
- No deployment in progress.
- No agent modifying the target membership concurrently — this is
  ultimately enforced by the CAS filter, but the operator SHOULD confirm
  no scheduled job could touch OrgMembership during the pilot window.
- Worktree/code version pinning captured (Section N).
- DB target confirmed (URI printed by the apply script's banner reviewed
  by the operator).

Do not schedule a specific arbitrary hour here — the tenant owner and the
operator jointly select the window.
