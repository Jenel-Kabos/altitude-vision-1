# HOTFIX-ZOHO-IMAP-SEEN-CHECKPOINT-1 — Matrice d'échec et de reprise

| Panne | Comportement | Preuve |
|---|---|---|
| Erreur métier sur un message (ex. échec Mongo transitoire lors de `InternalMail.create`) | `stats.errors++`, `checkpointStalled = true`, le message reste `UNSEEN`/non marqué avancé ; les UID suivants du même lot/cycle sont **quand même traités** (résilience pré-existante) mais le checkpoint ne dépasse jamais l'UID en échec | Test "échec métier sur un UID intermédiaire" : 113 réussit, 114 échoue, 115 réussit quand même (`imported:2, errors:1`), mais `findOneAndUpdate` est appelé avec `lastProcessedUid: 113`, jamais 114 ni 115 |
| Erreur de connexion IMAP (`ETIMEOUT`, `ECONNRESET`, etc.) | Propagée immédiatement (`throw connectionError \|\| error`), le cycle s'arrête, `stats.errors++`. Le checkpoint garde sa dernière valeur avancée avant l'erreur (rien n'est perdu de ce qui a réussi) | Comportement hérité, inchangé — tests réseau pré-existants toujours verts (10/10) |
| Échec de persistance du checkpoint lui-même (`ImapSyncCheckpoint.findOneAndUpdate` rejette) | `stats.errors++`, logué explicitement ("le prochain cycle réexaminera cette plage"), le cycle se termine proprement (logout, libération du lock, `isPolling` remis à `false`) — **ne bloque jamais** la fin du cycle | Test "échec de persistance du checkpoint" : `findOneAndUpdate` rejette, résultat `{imported:1, skipped:0, errors:1}`, `client.logout` bien appelé une fois |
| Crash process avant la fin du `finally` (jamais atteint) | Le checkpoint Mongo garde sa dernière valeur persistée avec succès (le cycle précédent). Au redémarrage, `resolveSyncOrigin` repart de cette valeur ; tout message traité entre-temps mais non encore persisté au checkpoint sera réexaminé et filtré par `zohoMessageId` (voir `_IDEMPOTENCE_MATRIX.md`) | Raisonnement direct sur le code (écriture unique et atomique en fin de cycle) — **NON CONFIRMÉ par test de crash réel**, non simulable de façon fiable en Jest |
| Aucun nouveau message trouvé | Aucune écriture de checkpoint (ni régression, ni écriture inutile) | Test "aucun nouveau message : le checkpoint existant reste inchangé" : `findOneAndUpdate` jamais appelé |
| Mailbox vide au bootstrap | Établit quand même un checkpoint de référence (`lastProcessedUid: 0`, `isReset:true`) pour éviter un rescan complet infini à chaque cycle tant qu'aucun message n'arrive | Test "mailbox vide au bootstrap : établit quand même un checkpoint de référence" |
| Trou (gap) entre le checkpoint et le prochain UID réel (ex. suppression de messages intermédiaires côté serveur) | La recherche `UID > lastProcessedUid` retrouve normalement le prochain UID existant, aucune erreur, aucun blocage | Test "UID avec un trou (gap) entre le checkpoint et le prochain message réel" : checkpoint à 100, prochain UID réel 105 → traité normalement, checkpoint avance à 105 |

## Politique de retry

Aucun retry actif au sein d'un même cycle au-delà de la résilience déjà existante (traiter les UID suivants malgré un échec sur l'un d'eux). La reprise se fait par le **prochain cycle cron naturel** (`*/5 * * * *`, inchangé) : tout UID non dépassé par le checkpoint y sera automatiquement réexaminé, protégé de toute duplication par `zohoMessageId`. Aucun mécanisme de backoff exponentiel n'a été ajouté — jugé disproportionné, la fréquence de 5 minutes suffisant à absorber une panne transitoire sans risque de perte (contrairement à l'ancien mécanisme `\Seen` qui perdait silencieusement et définitivement).
