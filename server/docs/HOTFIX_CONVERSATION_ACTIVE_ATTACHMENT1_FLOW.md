# HOTFIX-CONVERSATION-ACTIVE-ATTACHMENT-1 — FLUX COMPLET

## Upload → stockage → API → serialization → frontend → preview/download

1. **Frontend, sélection du fichier** — `MessagesPage.jsx`/`StaffInboxPage.jsx`, `<input type="file" accept="image/*,video/*,audio/*,application/pdf">` (`accept` = indication UI pour le picker natif uniquement, **contournable** par glisser-déposer ou par un appel API direct — jamais une frontière de sécurité, correctement non présentée comme telle).
2. **Upload HTTP** — `POST /api/messages`, `multipart/form-data`, champ `attachments` (jusqu'à 5 fichiers), route protégée (`protect`, `attachTenantContext`, `messageRoutes.js:24`, inchangé).
3. **Middleware multer** — `uploadAttachments = upload.array('attachments', 5)` (`server/config/cloudinary.js`) : **`fileFilter` rejette (400) tout fichier dont le `Content-Type` déclaré par le client est `text/html`/`application/xhtml+xml`/`image/svg+xml`** — barrière réelle avant tout code contrôleur, confirmée par `messageAttachmentMimeFilter.test.js`.
4. **Contrôleur** — `messageController.js::sendMessage` (lignes 45-69) : pour chaque fichier accepté par le filtre, `uploadPrivateAsset(file.buffer, { purpose:'conversation', ownerType:'Conversation', ownerId, filename: file.originalname, mimeType: file.mimetype })` — le MIME stocké (`asset.mimeType`) est **exactement** celui déjà validé par le fileFilter (jamais un MIME hors de l'allowlist).
5. **Stockage** — Cloudinary, asset privé (`secureStorageService.js`, non modifié, hors périmètre — mandat §38).
6. **Modèle `Message`** — `attachments: [{ asset, type: 'image'|'video'|'audio'|'file', nom, size, duration }]` (`models/Message.js:43-50`). `type` est une **catégorie grossière**, jamais un MIME réel.
7. **Sérialisation API (REST)** — `messageSerializer.js::serializeMessage` (via `sendMessage`/`getMessages`/`conversationController.js`) : `safePrivateDescriptor(asset, {...})` ajoute `mimeType`, `originalFilename`, `canPreview`, `canDownload`, `previewEndpoint`, `downloadEndpoint` — **certifié inchangé par ARCH-2C2**, non modifié ici.
8. **Sérialisation temps réel (Socket.IO)** — `messageController.js:214,226` émet `getIO().to(...).emit('new-message'/'new-staff-message', { conversationId, message })` avec le **document Mongoose brut** (pas `serializeMessage`) — confirmé volontairement inchangé (mandat §35, ARCH-2C2 a explicitement conservé ce payload brut). Sa sérialisation JSON implicite passe par le `toJSON` du modèle (`Message.js:69-76`), qui **n'inclut PAS `mimeType`/`originalFilename`** — seulement `hasPrivateFile`, `legacy`, `previewEndpoint`, `downloadEndpoint`, et les métadonnées brutes (`nom`, `size`, `type`, `duration`). **Conséquence pour la classification côté frontend** : un message reçu en direct via Socket.IO ne porte pas de MIME exploitable tant qu'il n'a pas été re-fetché via REST — documenté comme limite pré-existante, non introduite ni corrigée par ce hotfix (aucune modification Socket.IO autorisée, mandat §35).
9. **Frontend, réception** — `MessagesPage.jsx`/`StaffInboxPage.jsx`, `renderAttachment(att)` : `att.nom || att.originalFilename` (gère déjà les deux formes, REST et Socket.IO brut — code défensif préexistant, non modifié).
10. **Preview/Download** — `conversationService.js::openConversationAttachment(attachment, { download })` : un seul mécanisme pour les deux usages, `responseType:'blob'` → `URL.createObjectURL` → ancre `<a href=objectUrl target="_blank">` (preview) ou `<a href=objectUrl download=...>` (download) — **aucune classification MIME/extension**, mais voir `_THREAT_MODEL.md` : la préview d'un Blob dont le `type` est nécessairement une image/vidéo/audio/PDF (jamais HTML/SVG, contraint dès l'étape 3) ne peut pas déclencher d'exécution de code, quel que soit le mécanisme d'ouverture utilisé.
11. **Endpoint de service** — `GET /api/messages/:messageId/attachments/:attachmentId[?download=1]` → `messageController.js::downloadAttachment` : `Content-Type: attachment.asset.mimeType || 'application/octet-stream'` (toujours une valeur de l'allowlist de l'étape 3 pour un attachment `asset`-based), `Content-Disposition: inline|attachment`, `X-Content-Type-Options: nosniff` — déjà présent, non modifié.

## Chemin alternatif — attachments "legacy" (`url`-based)

`attachment.asset` absent mais `attachment.url` présent → `streamRemoteDocument({ url, name, res })` (`documentStreamingService.js`) proxy-streame l'URL distante en conservant le `Content-Type` de la réponse amont **tel quel, sans contrainte d'allowlist**. **Aucun chemin de code vivant trouvé** qui permette de créer aujourd'hui un attachment `Message` avec un champ `url` (recherche exhaustive de tous les `Message.create(...)`, deux occurrences seulement : `messageController.js::sendMessage`, qui ne construit jamais de champ `url`, et `conversationController.js` ligne 541, message de démarrage de conversation sans aucun attachment). Ce chemin ne peut concerner que des données historiques éventuelles, non créables via le code actuel — voir `_THREAT_MODEL.md`.
